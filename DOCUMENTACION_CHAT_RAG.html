Resumen ejecutivo

El chat no es un agente conversacional libre. Es un orquestador de respuestas de una sola pregunta, diseñado para privilegiar evidencia local y evitar alucinaciones sobre la partida.

01

Primero: reglas

ChatService normaliza la pregunta, busca el primer patrón regex compatible y ejecuta un handler especializado.

02

Luego: datos reales

Los handlers componen información del estado en vivo, recomendaciones, historial, Riot API, Data Dragon y análisis postpartida.

03

Finalmente: conocimiento o LLM

Las preguntas básicas consultan un corpus TF‑IDF. Si no hay coincidencia suficiente, el LLM opcional intenta responder.

Conclusión precisa: el sistema implementa RAG generativo cuando hay un LLM configurado: recupera hasta tres pasajes y los agrega al prompt. Sin LLM, conserva una degradación extractiva y devuelve el mejor pasaje local.

Flujo de una solicitud

Entrada y validación

El frontend envía {"question": "..."} a POST /api/chat. Pydantic exige entre 1 y 500 caracteres.

Normalización

_norm() convierte a minúsculas y elimina acentos mediante Unicode NFD. Esto permite que “línea” y “linea” coincidan con la misma regla.

Clasificación determinista

answer() recorre INTENTS. Al encontrar una regex válida invoca dinámicamente _handle_<intent>.

Obtención y composición

El handler consulta únicamente las fuentes necesarias. La respuesta se construye con plantillas de Python; para datos sensibles de la partida no interviene un generador libre.

Ruta de conocimiento

En game_basics y antes del fallback general, el corpus recupera hasta tres entradas. Exige score mínimo 0.12, cobertura de términos 0.60 y coincidencia con un título o tag; con LLM genera sobre esos pasajes y sin LLM devuelve el mejor.

Compuerta de dominio

Antes de enviar un fallback al LLM, _is_lol_question() exige un término específico de LoL, una frase conocida, un Riot ID o un nombre completo de campeón. Las consultas externas reciben un mensaje local y no consumen tokens.

Respuesta uniforme

Todos los caminos terminan en un objeto con answer, intent, disponibilidad, fuentes y tipo de fuente. La UI muestra el texto y las fuentes.

Tolerancia a fallos: una excepción dentro de un handler se captura, se registra y produce una respuesta honesta con data_available=false. Un fallo del LLM también vuelve a una respuesta local o de ayuda.

Cómo se realiza el RAG local

El archivo game_knowledge.py contiene once documentos sobre prioridad, objetivos, gank, visión, tempo y lore básico de Runaterra, Diana y Nasus.

Indexación al iniciar

Cada documento concatena title + text + tags. TfidfVectorizer normaliza minúsculas, elimina acentos y crea unigramas y bigramas con ngram_range=(1, 2).

documento = título + texto + tags
matriz = TF_IDF.fit_transform(documentos)

Recuperación por pregunta

La pregunta se transforma con el vocabulario ya entrenado. Se calcula similitud coseno contra toda la matriz y se selecciona únicamente el mejor documento.

query  = vectorizer.transform([question])
scores = cosine_similarity(query, matrix)[0]
best   = argmax(scores)
resultados = Top‑3(coseno(query, docs)) si score ≥ 0.12 y cobertura ≥ 0.60
Control contra falsos positivos: además del score TF‑IDF, cada candidato debe cubrir al menos 60% de los términos significativos. Así, “color del Barón” no acepta un documento que solo coincide con “Barón”. Las stopwords españolas tampoco aportan similitud artificial.

Ruta del LLM y degradación controlada

LLMClient usa una interfaz compatible con OpenAI y se configura mediante LLM_PROVIDER, LLM_API_KEY y, opcionalmente, LLM_MODEL.

Filtro previo

Una pregunta claramente externa, como “¿qué es Kubeflow?”, devuelve out_of_scope sin llamar al proveedor. Los nombres de campeón se comparan como palabras completas para evitar falsos positivos como Vi dentro de “servicio”.

Cuándo se llama

Solo en un miss de game_basics o cuando ninguna regex reconoce la pregunta. Las respuestas deterministas de items, historial, partida y ML no pasan por el LLM.

Qué recibe

Un system prompt de coach, la pregunta y, cuando hubo recuperación válida, los pasajes con sus títulos mediante context_note.

Fallback de Gemini

Si el modelo primario devuelve HTTP 503, se repite una vez con gemini-flash-lite-latest. No se cambia de modelo para errores no transitorios.

Fallo seguro

Timeout, error de red, JSON inválido o respuesta no exitosa producen None. El chat vuelve entonces al mensaje local disponible.

pregunta abierta
  ├─ fuera de LoL → mensaje local; no llama al proveedor
  └─ dentro de LoL + LLM configurado y con API key
       ├─ 200 → respuesta + aviso “generada por IA”
       ├─ Gemini 503 → retry con Flash Lite
       └─ otro fallo → None → respuesta local / ayuda

GET /api/chat/proactive reutiliza el mismo contrato. Selecciona una recomendación fuerte de gank, objetivo o item; si no existe, emite un consejo general o informa que no hay partida activa.

Hallazgos y recomendaciones

Observaciones derivadas del cableado real, no solo de los comentarios del código.

PrioridadHallazgoImpacto / recomendación
MediaChatContextBuilder y build_prompt() no están conectados.No asumir que el LLM conoce snapshot o historial. Si se integran, filtrar datos y usar el prompt estricto antes de pasar contexto real.
BajaLa verificación de cobertura es léxica, no una prueba semántica de answerability.Evaluar falsos positivos con un conjunto de preguntas y, al crecer el corpus, considerar embeddings o un reranker.
BajaEl LLM recibe pasajes recuperados, pero el constructor general de contexto sigue desconectado.Mantener separados los pasajes de conocimiento y los datos de partida; conectar solo campos de juego explícitamente permitidos.
BajaEl score de recuperación se calcula, pero no llega al contrato ChatResponse.Agregar metadata opcional si se necesita observabilidad o ajuste empírico del umbral.
BajaEl router regex es first-match y no reporta confianza.Añadir pruebas de colisiones al crecer los intents o migrar a un clasificador híbrido manteniendo handlers deterministas.
BajaLa compuerta de dominio usa un vocabulario controlado.Revisar términos rechazados en logs y ampliar la lista únicamente con conceptos inequívocos de LoL para evitar abrir temas externos.
BajaEl chat es stateless: cada petición contiene una sola pregunta.Es adecuado para seguridad y simplicidad; si se añade memoria, delimitar sesión, caducidad y datos permitidos.
BajaEl corpus sigue siendo pequeño y estático, aunque ahora recupera Top‑3.Para crecer: cargar documentos versionados, evaluar precision@k, cobertura y calidad final con preguntas reales.
Fortaleza principal: la separación entre datos de juego deterministas y generación abierta reduce el riesgo de inventar oro, items, historial o estado en vivo. La respuesta también conserva intent y fuentes, lo que facilita depuración y transparencia en UI.
